# Release and publication

The publication proposal uses GitHub for code and maintained documentation, Zenodo for a frozen complete research release, GBIF for biodiversity discovery, and a data paper for reviewed methods and contributor recognition. These products should identify and link the same release. The planned licence is CC BY 4.0 for first-party structured observation data and its associated metadata/documentation, and CC BY 4.0 is requested for the data paper. The rights holder, contributor attribution and permissions must be confirmed before public release; a build becomes a citable frozen release only through step 3 below.

## Prepare a release

1. Review scientific audit findings and document unresolved limitations, source selection and provisional seasons.
2. Commit, push and build. `output/zenodo/` holds the three research CSVs, descriptor and usage/column guides. The package licence applies to the first-party structured observation resources (`count`, `survey`, `taxonomy`) and original documentation. `report_text` and `paper_text` are curated extracts from third-party works and are excluded from the CC BY grant unless rights-holder permission is obtained; they stay in `output/text/`, outside the release.
3. Tag the release: `uv run python scripts/release_dataset.py vYYYY.N` (`--dry-run` first). It refuses a build from uncommitted code or another commit than HEAD, an unpushed commit, a failed check or a file changed since the build, and publishes `dataset.zip` (the `output/zenodo/` files and `metadata.json`, with each file's sha256) on a GitHub release. A release is never replaced: a correction is a new tag.
4. Zenodo, by hand: upload the files of `dataset.zip` to a new version of the counts record, reserve its DOI, and fill the webform from `output/README.md` (maintained in `docs/zenodo.md`; not an upload file). Name the tag in the version field.
5. GBIF, by hand: set the DOI in `config/gbif.json` (currently `10.5281/zenodo.23598005`) and generate the Event/Occurrence CSVs from the same tables (`export_gbif.py`). The export retains Avibase concept IDs, uses eBird names for identical concepts and links each record to the research release through `dcterms:references`. Use CC BY 4.0, subject to rights-holder confirmation; record the same machine-readable licence in IPT/EML. Agree persistent exported IDs, geography, publisher/IPT and public attribution; complete EML with the reciprocal release relationship and validate interpreted timing, taxonomy, zero/presence and direction categories. See [the GBIF guide](gbif.md).
6. defile-passage builds from the tag (`build_explore.py --dataset vYYYY.N`) and publishes the Explore website and its passage tables, which go to a second Zenodo record derived from the counts record. defileViz, the forecast and the paper's statistics name the same tag. Publish future seasons as new versions, clearly marking unfinished seasons provisional.

Detailed weather, narratives, native IDs, processing notes and crosswalks remain in the research product even when omitted from GBIF. The `report_text` and `paper_text` extracts remain separate from the Zenodo deposit and outside the CC BY grant until rights are cleared. Software code has no licence declared by this data licence; choose and apply a separate software licence before treating the code repository as an openly licensed code release. Observer attribution and free text require the agreed public-field policy.

## Paper and coordination

The manuscript belongs in paper/ (local evidence: `paper/manuscript.qmd`), with figures and summaries generated from the cited release. The recorded proposal is Biodiversity Data Journal; journal fit, fees, funding and authorship remain decisions for the team. Journal and precedent research (local evidence: `paper/research/publication.md`) is separate from maintained dataset methods. The organiser email draft (local evidence: `paper/coordination/email-organisateurs.md`) gathers permissions, credit and scientific clarifications; it is not a sent message or a decision record.
